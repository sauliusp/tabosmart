# Optional local names and explanation wording

Tabosmart's initial tab suggestions, measured reasons, and fallback group names are deterministic and appear immediately. Local AI generates short group names and helps choose clear explanation wording. In 1.4.0, AI assistance defaults on for a fresh or missing preference. A fresh installation starts tab observation and history analysis after Chrome grants the required permissions, with a nonblocking disclosure and no additional onboarding gate. Stored pauses or erasure remain paused. AI naming and candidate discovery run only while observation and assistance are enabled, the relevant workspace is visible and the browser model configuration is available. Existing false preferences stay off. The user can switch AI off. Enabling assistance does not itself authorize an automatic model download; setup remains an explicit user action. AI cannot close, move, save or rank tabs. Optional discovery may propose new inferred memberships using exact title evidence; the backend and user review determine whether those proposals can be applied. The module does not read page bodies. It has no cloud AI fallback, model service key, telemetry request, or remote inference code.

## Current browser contract

Checked against Chrome's primary documentation on 8 September 2026. Chrome documents its Prompt API for extensions from version 138. Presence alone is insufficient: availability depends on model, device, language, and session options. The expired `aiLanguageModelOriginTrial` permission must not be added. The Prompt API runs in a document, not a service worker. Tabosmart imports the module in its extension interface. No host or scripting permissions are needed for local naming. [Prompt API](https://developer.chrome.com/docs/ai/prompt-api).

The API reports `unavailable`, `downloadable`, `downloading`, or `available`. Tabosmart adds interface states for checking, preparation, and check failure. Every status includes accessible text. Both features share the browser model. **Model availability, setup outcomes, and individual inference outcomes are separate.** A name or wording timeout leaves the model ready when Chrome still reports available. Passive checks call `availability()` only. Explicit setup calls `create()` directly in a user click, with progress, and releases the session afterward. [Capability and activation requirements](https://developer.chrome.com/docs/ai/get-started).

An unavailable result is an observation, not a diagnosis. Device resources, policy, model support, and language options may affect it; the extension does not claim to identify which condition caused it. Settings link to Chrome's [getting started guide](https://developer.chrome.com/docs/ai/get-started) and [Prompt API documentation](https://developer.chrome.com/docs/ai/prompt-api) for current requirements. Core suggestions and the measured explanations continue to work. A ready indicator describes availability only. `lastInferenceAt` is null until a valid result has actually completed locally for that feature.

Naming declares English for the system instructions plus recognized title languages as input, and the selected group-name language as output. Chrome currently documents Prompt API support for English, Japanese, Spanish, German and French. Lithuanian and Polish naming therefore retain the immediate metadata fallback without a model request. A request-specific availability check uses the same options as session creation; unavailable or downloading language configurations fall back without starting setup. The shared base readiness check and vetted English explanation wording still use English. Automatic naming requires a clear title-language majority; explicit settings take precedence. The detector is a bounded heuristic, so short or ambiguous metadata can remain undetermined. [Naming policy and limits](MULTILINGUAL-GROUPING.md) Do not advertise other Chromium browsers, mobile support, or successful local model inference without testing those environments. [Language options](https://developer.chrome.com/docs/ai/prompt-api#add_expected_input_and_output).

## Module contract

`extension/local-ai.mjs` exports:

| Function                          | Result and call requirement                                                                                                                                                                                                                                                               |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `getCapabilities(onStatus?)`      | `{names, explanations}`; each capability has `state`, `label`, `detail`, `progress`, `errorCode`, `errorSource`, `lastInferenceAt`, `lastRequest`, and `lastSetup`. Optional callback receives an immediate checking snapshot and the resolved state. Does not create models or download. |
| `setup(kind, onProgress?)`        | `kind` is `names` or `explanations`. Call directly in a click. Resolves to a capability, including errors. Explicitly permits Chrome's model setup/download. Both features share one setup request.                                                                                       |
| `suggestName(tabs, context?)`     | Short string or `null`. Ready model only. Input is up to 16 non-incognito titles/domains plus bounded grouping signal and fallback context. Caller keeps the deterministic name on null.                                                                                                  |
| `enhanceExplanation(suggestion)`  | Exact vetted candidate string or `null`. Ready model only. Selects from engine-provided `explanationVariants`; rejects arbitrary generated wording. Render `suggestion.reason` before calling.                                                                                            |
| `cancelLocalAI({preserveSetup}?)` | Stops active/queued inference; explicit cancellation also aborts setup. On `pagehide`, preserveSetup: true leaves the active setup controller un-aborted.                                                                                                                                 |
| `resetLocalAIData()`              | Explicit erase: stops active and queued work and clears interface-owned cached wording, failures, inference timestamps, and request budget. Leaves Chrome's browser-owned model intact.                                                                                                   |

Progress receives `{state, progress}`, where progress is a fraction from 0 to 1 or null. UI callback failures cannot prevent cleanup. Setup has a **10-minute idle watchdog**, refreshed only when Chrome reports a genuine increase in download progress. There is no short absolute download limit: a large, slow download continues while reported progress advances. Repeated percentages do not extend a stalled operation forever. After 100%, Chrome has up to 10 minutes to finish creating the session. The watchdog is cleared when setup finishes; late progress cannot restart it. Active naming sessions stay capped at 30 seconds, explanation wording sessions at 15 seconds, and capability inspection at 5 seconds. Sessions are destroyed after completion, failure, cancellation, or late completion following cancellation. These deadlines stop Tabosmart's request; Chrome controls its model download lifecycle. Failures keep the deterministic wording.

`lastRequest` is null before a request, then contains `state` (`running`, `succeeded`, `failed`, or `cancelled`), safe `detail`, `errorCode`, `startedAt`, and `completedAt`. It records the latest request for that feature, not whether the model is installed. `lastSetup` is shared between both capabilities and contains a completed setup's `state` (`succeeded`, `failed`, or `cancelled`), safe `detail`, `errorCode`, and `completedAt`. Both are historical interface data. They never override a fresh browser availability result. The UI must label these as request/setup outcomes rather than diagnosing model availability from them.

## Lifecycle and truthful status

| State          | Observable meaning                                                                                                                                                                                                                       |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `checking`     | A passive browser availability check is pending. It says nothing yet about support.                                                                                                                                                      |
| `unsupported`  | The API is absent or Chrome reports unavailable for the requested options.                                                                                                                                                               |
| `downloadable` | Chrome reports that a download is needed. Only explicit setup can start it.                                                                                                                                                              |
| `downloading`  | Chrome reports an ongoing download or a live progress event is below 100%.                                                                                                                                                               |
| `preparing`    | Explicit setup has called `create()` but creation has not resolved. This is also the state after a 100% download event while Chrome initializes the model.                                                                               |
| `ready`        | Chrome reports available, or the explicit `create()` call has successfully resolved. A download percentage alone never sets this state.                                                                                                  |
| `error`        | A passive availability check failed (`errorSource: 'availability'`), or an explicit setup call is returning its immediate failure (`errorSource: 'setup'`). Individual inference failures are recorded in `lastRequest`, not this state. |

An explicit setup starts with **Preparing local AI** and no invented percentage because the module has not yet received a download event. During setup, capability checks return its actual latest phase and live progress, including preparation after 100%. They do not overwrite preparation with a generic downloading state. After setup settles, passive checks return Chrome's actual state; a later `available` result recovers to ready even if the previous setup failed. The old setup outcome remains separately available in `lastSetup`. A failed request never turns available into unavailable or implies that another model download is needed. Availability check failures say **Could not check model** and offer a passive check retry, which does not create a session or start a download.

Progress, failures, inference timestamps, and prepared sessions are not persisted. Closing the interface cancels its work and releases sessions. Reopening queries Chrome again: a continuing download can be reported without a percentage, and a removed model can report download needed. It never restores an old 100% bar or assumes a previous ready session still exists. The separate saved `aiEnabled` preference is controlled by the engine and UI; an enabled preference does not imply model readiness.

Erasing Tabosmart data also clears the AI module's interface-owned state. Old setup callbacks, inference results, and cancellation errors cannot repopulate erased caches or overwrite a new request. Closing an ordinary review dialog must not cancel an unrelated model download. The UI discards name results when their original review is no longer open.

An idle timeout says that **Tabosmart stopped waiting**, not that Chrome is unsupported or that Chrome's download was cancelled. Retrying asks Chrome about its current model through a fresh setup operation. Old timed-out progress callbacks and late-created sessions cannot overwrite the retry's state. `ai-status-watch.mjs` passively refreshes waiting states approximately every five seconds while the interface is visible and optional AI is enabled. It performs no model creation, avoids overlapping checks, stops on opt-out, and checks again on the UI's visibility or focus refresh. This observes current availability after reopening; it does not keep the closed page or its progress listener alive. On pagehide, both UI and module cleanup preserve the active setup AbortController while cancelling inference and disconnecting activity reports. An explicit opt-out or erasure still cancels local setup. Chrome separately documents that its triggered download continues after the initiating tab closes. [Model management](https://developer.chrome.com/docs/ai/understand-built-in-model-management#initial_model_download)

Normal extension installation targets the stable Chrome extension API from version 138 and does not ask the user to enable developer experiments or browser AI flags. Eligibility still varies. Current requirements belong in the official help links, while the extension keeps offering its deterministic names and explanations.

Returned names are limited to 36 characters and four words. HTML-like output, control characters, links, multiline text, and overlong names are rejected. The naming prompt uses up to 16 titles (160 characters each), parsed domains (253 characters each), a whitelisted grouping signal, and a fallback label capped at 60 characters. Full URLs, query strings, page content, and arbitrary context fields are not included. It asks the model to generate a useful common project/task/topic name when that meaning is supported, otherwise a literal site/topic label. Content words must appear in the title/domain evidence (with simple plural normalization); neutral organizing words such as work, research, notes, and planning may be added. At least one non-generic evidence word is required. This rejects invented subject words and wholly generic output. Lexical grounding is a constraint, not a guarantee that a name is useful; names remain editable. Render accepted output with `textContent`, never HTML. Names must not be presented as evidence.

Translation is not part of 1.4.0. Any future translation experiment must meet the nonblocking, bounded-work and measured-performance requirements in [the multilingual design note](MULTILINGUAL-GROUPING.md#future-translation-gate). No translation latency or resource benchmark has been performed.

## General candidate discovery

`discoverGroups(tabs, options)` runs ready-only structured Prompt API inference on at most 24 current eligible tabs per request. `group-discovery.mjs` validates real IDs, exact informative title quotes, bounded names and eligibility. `proactive-discovery.mjs` schedules sequential automatic passes with cooldowns and error backoff, cancellation, 128-entry exact-input caching and inferred concept hints for bounded cross-batch comparisons. It does not stop after 72 tabs or require a manual continuation. Results are explicitly inferred and may be wrong. Only backend-revalidated candidates enter review; no model action is automatic. Discovery has its own actual activity and request outcome; failure does not replace model readiness. No publisher-domain catalog is present. The non-AI metadata engine separately uses explicit category vocabulary, URL resource structure and local context. See [the complete contract and limits](MULTILINGUAL-GROUPING.md).

## Proactive names

`proactive-names.mjs` exports `createProactiveNames({generate, onName, maxAutomaticAttempts})` and `evidenceKeyFor(suggestion)`. The default generator is the real Prompt API naming path above, not explanation-variant selection. Initial grouping membership remains deterministic. Separate optional discovery can add inferred candidates with exact title evidence; it is not this naming controller.

| Method                                             | Contract                                                                                                                                                                                   |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `sync(suggestions, {enabled, available, visible})` | Queue only group proposals when all three conditions are true. `enabled` must include both enabled observation and the AI preference. Returns a promise for the current queue to settle.   |
| `whenIdle()`                                       | Wait for the current queue, allowing the interface to prioritize names before optional explanation wording.                                                                                |
| `getName(suggestion)`                              | Return `{name, evidenceKey, source: 'local-ai'}` for a cached, valid generated name with exactly matching evidence, otherwise null.                                                        |
| `request(suggestion, {retry})`                     | Manual naming shares the same evidence/cache/pending request handling. Explicit `retry: true` can retry unchanged failure or refine a generated name outside the automatic budget.         |
| `stop()`                                           | Discard queued work, resolve current scheduler requests/waits, and suppress late results. The interface also calls `cancelLocalAI({preserveSetup}?)` to stop actual model work on opt-out. |
| `reset()`                                          | Stop and clear generated cache, failure-attempt records, and the automatic budget on erase. The interface also calls `resetLocalAIData()`.                                                 |

The optional `onActivity({running, queued})` callback reports actual controller work. The UI uses it for the separate naming note; cancellation clears the note and late results cannot revive it. It does not report a percentage or imply that the core tab check is waiting on AI.

Existing native-group names and recalled confirmed names are excluded from automatic naming. At most ten automatic name attempts run per interface lifetime by default. Requests run one at a time; pending identical evidence deduplicates. The exact key includes suggestion identity/reason/signal/fallback, naming-language preference and every member's tab ID, exact URL, title, window, and group. Member ordering does not affect the key. Changing evidence invalidates lookup and suppresses any older in-flight result. Successful names and attempt records are capped at 128 entries. Unchanged failures do not continuously retry. Only a valid generated name that differs from the deterministic fallback receives a cache entry and `onName({suggestionId, evidenceKey, name, source: 'local-ai'})` callback. Fallbacks never receive generated provenance.

While a review is open, the interface can call `sync([], readyContext)` to freeze automatic proposals and retain manual naming. An explicit manual request can adopt a still-running automatic request only for the exact same evidence. The interface freezes review fields and guards manual completion against changed selection, evidence, user edits, opt-out, and closed reviews. Controller callbacks never create or rename Chrome groups. Hidden/disabled contexts stop new queue work and discard stale output; core fallback names stay available immediately.

## Faithful explanation selection

For supported wording signals, the engine creates two complete phrasings from the same measured fields: duplicate URL count, site and ungrouped count, shared title words, observed switches, or observed inactivity days. The first candidate is exactly the deterministic reason. AI-discovered candidates keep their single quoted-evidence reason and do not request wording selection. Duplicate and inactivity candidates preserve their cautions. Action confirmation and recovery limitations stay outside this wording choice and remain unchanged.

The model receives only those complete candidate strings with numeric IDs. It returns a single integer ID. The module rejects generated prose, extra claims, malformed IDs, out-of-range values, incomplete candidate lists, and private-tab requests. It returns the selected original string, never the model's text. This is **constrained AI wording selection**, not open-ended AI explanation generation. It cannot introduce unsupported specifics. The UI may say that local AI helped with wording only after a valid selection succeeds.

Naming, candidate discovery and explanation requests share one sequential inference queue, preventing competing live inference sessions. Identical pending name requests deduplicate. Explanation requests also deduplicate pending work and cache results by suggestion ID, deterministic reason, and candidate set. At most five explanation inference attempts run per interface lifetime or explicit setup/retry. A changed reason invalidates its cached result. Unavailable AI never triggers a download. Cancellation stops active and queued work; old outcomes cannot overwrite newer requests. Explicit setup releases active inference and invalidates queued work synchronously before creating its setup session, preserving the click's user activation. The UI must show the deterministic reason immediately and update only when the same suggestion and reason are still visible. Failed or rejected selection returns null and leaves that reason in place. The service worker never runs model inference. Visible workspace discovery may schedule bounded enrichment after current metadata settles.

## Privacy boundaries

Naming inference uses supplied tab titles, parsed domains, and bounded group context, with no incognito tabs. The proactive controller's exact cache key also uses supplied tab IDs, exact URLs, titles, windows, and groups solely in interface memory to reject stale results; full URLs are not sent to the model. Explanation selection uses only the engine's candidate phrasings, which can include a domain, shared title words, or measured activity counts. Neither model helper reads page bodies, forms, bookmarks or browser history. The separate history index uses required API access for local aggregate evidence and suggestion ordering; that does not grant the model history access or ranking/action authority. Generated-name and explanation caches remain in the current interface's memory, with no storage writes. Metadata and candidate contents are treated as untrusted source material and the model has no tools or actions. A generated group name may still be unsuitable. The user can keep the fallback name or rename the group.

Chrome says inference runs locally and does not send model input to Google or third parties. Initial model setup requires a network download, distinct from transmitting browsing content. Chrome may remove or update its model. Do not describe AI setup as requiring no network, or describe a browser's total network activity as Tabosmart telemetry. The module itself contains no `fetch`, XHR, WebSocket, analytics, or remote model calls. A real network audit of the full extension is still required to substantiate broader privacy claims. [Model, hardware, and download requirements](https://developer.chrome.com/docs/ai/get-started#hardware).
